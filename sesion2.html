1. Primer paso: llevar el repositorio JavaScript existente a TypeScript

Partimos del repositorio ControlLabs existente y convertimos toda la aplicación a TypeScript. No mantenemos dos versiones del código ni creamos otro repositorio: al terminar, el código fuente de la aplicación queda en TypeScript y Git conserva los commits históricos de JavaScript.

🧭

Antes de tocar archivos: proteger el trabajo existente

Abrimos la carpeta del repositorio existente y comprobamos su estado. Si hay cambios pendientes, se guardan en un commit antes de continuar. La rama de migración reemplaza la implementación JavaScript; no se mantiene una segunda versión activa. Los commits previos siguen disponibles en la historia del repositorio.

# Desde la carpeta del repositorio existente

git status

git switch main

git pull --ff-only origin main

git switch -c feat/migracion-typescript

git log --oneline -5

Si la rama ya existe, se cambia a ella en vez de crearla otra vez. No ejecutar git init: eso iniciaría otro repositorio y no es necesario para actualizar este proyecto.

📦

Instalar TypeScript y preparar compilación

Conservamos las dependencias existentes (por ejemplo, Express, CORS y dotenv) y añadimos TypeScript, el ejecutor de TypeScript para desarrollo y los tipos de las librerías que usamos.

npm install -D typescript tsx @types/node @types/express @types/cors

npx tsc --init

En package.json se agregan scripts como "dev": "tsx watch src/server.ts", "build": "tsc" y "start": "node dist/server.js". Se ajusta tsconfig.json para compilar src hacia dist usando CommonJS, acorde con el proyecto base.

La Clean Architecture se conserva; toda la implementación pasa a TypeScript

Se portan todas las fuentes de la aplicación a TypeScript, pero la práctica de esta sesión modifica solo el montaje de rutas y sus controladores HTTP. Actualizar los imports y eliminar los fuentes JavaScript ya portados después de comprobar la compilación.

Archivos de esta práctica:

src/app.ts

src/server.ts

src/routes/index.ts

src/routes/loan.routes.ts

src/controllers/loan.controller.ts

Se reemplaza cada fuente JavaScript por su equivalente TypeScript, se actualizan imports y se corrigen los diagnósticos del compilador. Después de portar el comportamiento y pasar pruebas, quitar el fuente antiguo con git rm ruta/al/archivo.js; revisar que no queden imports hacia archivos antiguos. No hacer reemplazos globales a ciegas.

Estado final: se versionan las fuentes .ts; el build genera dist/*.js porque Node ejecuta JavaScript. Esa carpeta es salida compilada, se ignora en Git y no es una segunda implementación que haya que mantener.

Configurar Git para el proyecto TypeScript

Se mantienen fuera del repositorio los secretos y artefactos generados; sí se versionan package-lock.json y la configuración de TypeScript para que el equipo reproduzca la instalación.

.env

!.env.example

Crear .env.example solo con nombres de variables y valores de ejemplo no secretos.

Verificar y actualizar el repositorio remoto

Comprobar build y pruebas. Después de eliminar las fuentes antiguas, git ls-files 'src/**/*.js' debe devolver cero resultados. Revisar el diff, guardar la migración en un commit y publicar la rama. El remoto conserva el historial previo y permite abrir una revisión antes de integrar.

Flujo empresarial: ramas y commits documentados

Cada tarea vive en una rama corta; los cambios se integran a main mediante Pull Request revisado.

Ramas: tipo/descripcion-corta

Conventional Commits

Formato tipo(alcance): resumen en imperativo. Cada commit explica un cambio coherente; evitar “cambios” o “avance”.

2. La Ruta del Viajero: ¿Qué ocurre cuando el cliente hace una petición HTTP?

Comprendiendo el ciclo de vida completo de la comunicación cliente-servidor antes de escribir código.

💻

1. El Cliente (Frontend / Postman)

Un navegador web (ej: la interfaz de ControlLabs) o una herramienta como Postman envía un paquete HTTP indicando un método (GET, POST), una URL (/api/v1/loans) y opcionalmente un cuerpo JSON (req.body).

🚦

2. El Enrutador (Router de Express)

El servidor entrega la petición a la aplicación configurada en app.ts. Sus routers analizan la URL y el verbo HTTP y dirigen la solicitud al controlador correspondiente; si no hay coincidencia, Express responde 404.

🧠

3. El Controlador & Respuesta

El Controlador lee los datos de la petición, valida su formato y decide qué código HTTP y cuerpo devolver con res.status(200).json({...}).

3. Enrutamiento Modular en Express con TypeScript (`express.Router()`)

Cómo desacoplar las rutas del archivo principal para mantener un proyecto ordenado y profesional.

📂

¿Por qué usar `express.Router()`?

Si escribiéramos todas las rutas en un solo archivo server.ts, tendríamos miles de líneas inmanejables. La clase Router() de Express permite crear enrutadores modulares independientes (ej: user.routes.ts, loan.routes.ts).

// 1. Importar y crear router

import { Router } from 'express';

const router = Router();

// 2. Definir endpoints

router.get('/saludo', (req, res) => {

  res.send('Hola SENA ADSO');

});

export default router;

🌐

Mapeo de Verbos HTTP en el Router

El enrutador asocia cada método HTTP con una acción CRUD específica sobre los recursos del sistema:

router.get()

Consultar recursos (Lectura)

router.post()

Crear nuevo registro

router.put()

Modificar recurso existente

router.delete()

Borrar recurso

4. Los Controladores: Procesar la Solicitud y Responder

La ruta identifica el handler; el controlador lee y valida la entrada HTTP y construye la respuesta correspondiente.

🧠

¿Qué es un Controlador en TypeScript?

El controlador es el handler HTTP que recibe req y res. Su estructura estable es recibir la petición, invocar la operación correspondiente y traducir su resultado a una respuesta HTTP. En este momento la llamada queda señalada; no agregamos validaciones de negocio que luego cambiarían al incorporar las demás capas.

  • Recibe los datos HTTP desde req.body, req.params o req.query, según el endpoint.
  • El comentario TODO marca dónde se conectará la operación futura y cómo su resultado se convertirá en respuesta HTTP.
  • Mientras esa operación no existe, devuelve 501 Not Implemented de forma honesta; no inventa datos ni afirma que guardó algo.
// 📁 src/controllers/ejemplo.controller.ts
import { Request, Response } from 'express';

export class EjemploController {
    public static saludarSena = (req: Request, res: Response): void => {
        // TODO: invocar aquí la operación correspondiente y responder con su resultado.
        res.status(501).json({
            success: false,
            mensaje: 'La operación todavía no está implementada.'
        });
  };
}

5. La Articulación: Cómo una Ruta Invoca a su Controlador

El momento clave: uniendo los cables entre el enrutador modular y las funciones lógicas del controlador.

🔗 ¿Cómo se conectan en código?

El archivo de rutas importa el controlador y le asigna la función correspondiente a cada verbo HTTP sin escribir lógica dentro de la ruta. Observa el esquema exacto:

// 📁 src/routes/ejemplo.routes.ts (El Enrutador)
import { Router } from 'express';
import { EjemploController } from '../controllers/ejemplo.controller';

const router = Router();

// Vinculación: Ruta -> Método Controlador
router.get('/saludo', EjemploController.saludarSena);

export default router;
// 📁 src/routes/index.ts (Agregador de recursos)
import { Router } from 'express';
import ejemploRoutes from './ejemplo.routes';

const router = Router();
router.use('/ejemplo', ejemploRoutes);

export default router;
// 📁 src/app.ts (Configuración de Express)
import express from 'express';
import apiRoutes from './routes';

const app = express();
app.use(express.json());
app.use('/api/v1', apiRoutes);

export default app;

💡 Conclusión pedagógica:

app.ts configura Express y routes/index.ts reúne routers por recurso. Cuando llega GET /api/v1/ejemplo/saludo?nombre=Ana, Express combina /api/v1 + /ejemplo + /saludo y el router entrega la solicitud a EjemploController.saludarSena. El query queda disponible en req.query.nombre; el TODO indica dónde se conectará la operación futura. Así app.ts no se convierte en un inventario de endpoints.

6. Manejo de Parámetros (`req.params`) y Consultas (`req.query`) con Validación

Extrayendo datos dinámicos desde la URL y validando que el cliente envíe la información correcta.

🔗 Route Parameters (`req.params`)

Identificadores Obligatorios en la Ruta

Se definen con dos puntos (:id). Sirven para identificar un recurso único.

// Ruta: /loans/:id

const { id } = req.params;

console.log(`Buscando préstamo ID: ${id}`);

🔍 Query Parameters (`req.query`)

Filtros y Paginación Opcionales

Se envían después del signo ? en la URL. Ideales para filtros de búsqueda.

// URL: /loans/search?room=302&status=PENDING

const { room, status } = req.query;

Desglose de cada endpoint: path, parámetros y propósito

Los prefijos se componen: app.ts monta /api/v1, routes/index.ts monta /loans, y loan.routes.ts define el path relativo. Un path sin :param no lee req.params; query y body son entradas distintas.

Ruta finalreq.paramsreq.queryBody y resultado
POST /api/v1/loansNinguno; no hay segmentos variables.Ninguna en este ejemplo.El handler recibe req.body. El TODO indica que después llamará al servicio; por ahora responde 501.
GET /api/v1/loans/search?room=302&startDate=2026-10-01&endDate=2026-10-15Ninguno. search es literal, no parámetro.room, startDate, endDate quedan disponibles en req.query.Sin body. El handler responderá 501 hasta que se conecte la consulta.
GET /api/v1/loans/801id es obligatorio en /loans/:id; Express lo entrega como texto en req.params.id.Ninguna.Sin body. El handler usa el ID como entrada y responde 501 hasta conectar la consulta.
PUT /api/v1/loans/801/acceptid es el segmento variable; accept es literal.Ninguna.Sin body. El handler usará el ID al conectarse la operación de aceptación; ahora responde 501.

Route params: en /loans/:id, una petición a /loans/801 da req.params.id === '801'. El valor llega como string; el handler lo recibe y lo pasará a la operación que se conecte después.

Query params: aparecen tras ? y se separan con &. Express los expone en req.query; por ejemplo ?room=302&startDate=2026-10-01. Son texto y deben validarse; suelen ser opcionales.

Definir primero paths estáticos como /search y luego los dinámicos como /:id mejora la lectura y evita colisiones si se agregan patrones más amplios.

7. Práctica ControlLabs: Router y Controller

En esta sesión trabajamos solo estas dos piezas: el router identifica el endpoint; el controller recibe la solicitud y construye la respuesta HTTP.

Ensamble de URLs

La ruta del recurso se define relativa al prefijo /loans. El agregador de rutas lo monta bajo ese prefijo y app.ts monta el agregador en /api/v1. En esta práctica los handlers no consultan ni guardan datos: lo indican con una respuesta explícita cuando la operación está pendiente.

// 📁 src/routes/loan.routes.ts: método + path → handler
import { Router } from 'express';
import { LoanController } from '../controllers/loan.controller';

const router = Router();

router.get('/search', LoanController.getLoansByFilter);
router.post('/', LoanController.createLoan);
router.put('/:id/accept', LoanController.acceptLoanInventory);
router.get('/:id', LoanController.getLoanById);

export default router;
// 📁 src/routes/index.ts: agrupa los routers
import { Router } from 'express';
import loanRoutes from './loan.routes';

const router = Router();
router.use('/loans', loanRoutes);

export default router;
// 📁 src/controllers/loan.controller.ts: handlers y puntos de extensión
import { Request, Response } from 'express';

export class LoanController {
  public static createLoan = (req: Request, res: Response): void => {
    // TODO: llamar al servicio con req.body y responder 201 con el préstamo creado.
    res.status(501).json({
      success: false,
      message: 'El registro de préstamos todavía no está implementado.'
    });
  };

  public static getLoansByFilter = (req: Request, res: Response): void => {
    // TODO: tomar los filtros de req.query, llamar al servicio y responder con los resultados.
    res.status(501).json({
      success: false,
      message: 'La consulta del historial todavía no está implementada.'
    });
  };

  public static getLoanById = (req: Request, res: Response): void => {
    const { id } = req.params;
    // TODO: pasar id a la operación de consulta y responder con el préstamo encontrado.
    res.status(501).json({
      success: false,
      message: `La consulta del préstamo ${id} todavía no está implementada.`
    });
  };

  public static acceptLoanInventory = (req: Request, res: Response): void => {
    const { id } = req.params;
    // TODO: pasar id a la operación de aceptación y responder con el resultado.
    res.status(501).json({
      success: false,
      message: `La aceptación del préstamo ${id} todavía no está implementada.`
    });
  };
}

Qué comprobar en cada petición

En esta etapa los handlers dejan visible el punto de extensión: recibirán req.body, req.query o req.params.id, llamarán a la operación correspondiente y mapearán su resultado a HTTP. Mientras esa operación no esté conectada, responden 501 sin afirmar que validaron o guardaron datos.

Qué hace cada función del controlador

Los cuatro métodos estáticos son handlers que el router conecta con cada endpoint. Sus firmas y el mapeo HTTP se conservarán; el cuerpo con TODO y 501 es temporal hasta conectar las operaciones posteriores.

FunciónQué recibe y haceQué responde
createLoanEs el handler de POST /loans. En el TODO usará req.body como entrada para la futura operación de creación.501 temporalmente. Más adelante responderá con el resultado real de la creación, normalmente 201.
getLoansByFilterEs el handler de GET /loans/search. En el TODO usará los filtros que llegan en req.query.501 temporalmente. Más adelante responderá con el historial encontrado.
getLoanByIdEs el handler de GET /loans/:id. Lee el identificador de req.params.id.501 temporalmente. Más adelante responderá con el préstamo correspondiente o el status adecuado.
acceptLoanInventoryEs el handler de PUT /loans/:id/accept. Toma el ID de req.params.id para la futura operación.501 temporalmente. Más adelante responderá con el resultado de la aceptación.

Qué se conserva al avanzar: los paths, nombres de handlers, parámetros HTTP, firmas (req, res) y el lugar donde se forma la respuesta. Se reemplazan los TODO por llamadas a las operaciones que se enseñen después; no hay validación de negocio provisional que luego tengamos que mover.

8. Probar los endpoints con Thunder Client

Levanta la API, configura cada petición en Thunder Client y compara la respuesta observada con la respuesta temporal definida por los handlers.

Antes de probar: en la terminal, entra a la carpeta del proyecto TypeScript y ejecuta npm run dev. En estos ejemplos se asume que el servidor escucha en el puerto 3000; si tu PORT es otro, reemplaza ese número en las URLs. Mantén esa terminal abierta mientras haces las peticiones.

Thunder Client: configurar cada petición paso a paso

  1. Abre Thunder Client en la barra lateral, crea la colección ControlLabs y elige New Request.
  2. En el selector de método y la caja de URL configura POST http://localhost:3000/api/v1/loans. Pulsa Body → JSON y completa las propiedades del ejemplo. Thunder Client normalmente agrega el header automáticamente; comprueba en Headers que aparezca Content-Type: application/json.
  3. Para buscar, cambia el método a GET y usa http://localhost:3000/api/v1/loans/search. En Query agrega room=302, startDate=2026-10-01 y endDate=2026-10-15. La herramienta los agrega a la URL después de ?; no van en el body.
  4. Para el parámetro de ruta elige GET y escribe http://localhost:3000/api/v1/loans/801. El valor 801 ocupa el segmento :id.
  5. Para aceptar, elige PUT y escribe http://localhost:3000/api/v1/loans/801/accept. No hay body en este handler provisional.
  6. Pulsa Send, revisa status y respuesta, y guarda cada request en la colección.

En el body del POST crea estas propiedades: aula (texto), numeroPC, mouse y teclados (números), nombreGuardaEntrega e instructorRecibe (texto). En JSON los textos llevan comillas dobles; los números no.

{
    "aula": "Sala 302 TI",
    "numeroPC": 20,
    "mouse": 20,
    "teclados": 20,
    "nombreGuardaEntrega": "Ana Perez",
    "instructorRecibe": "Carlos Ruiz"
}

¿Por qué Content-Type?

El body contiene bytes; el header Content-Type le dice al servidor en qué formato se enviaron. Al seleccionar JSON, se indica application/json, y el middleware express.json() puede interpretarlo y colocarlo en req.body.

Se usa cuando la petición envía un body JSON, como el POST. Un GET con filtros no lleva body: sus query params van en la URL, así que no requiere ese header. El PUT actual tampoco envía body; no se agrega Content-Type si no se manda contenido.

No confundir: Content-Type describe lo que el cliente envía; Accept expresa el formato que el cliente prefiere recibir.

Importante: recibir 501 Not Implemented en las cuatro rutas registradas es lo esperado ahora: confirma que el router encontró el handler y que este marca la operación pendiente. No significa que los datos se hayan creado, buscado o actualizado. Cuando esas operaciones se implementen, se actualizan las respuestas esperadas y se repiten las pruebas.
